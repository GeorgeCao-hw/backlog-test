对指定 PR 进行代码检视，输出结构化检视报告。

## 输入参数
- $ARGUMENTS: PR 编号或 PR URL（如 `55` 或 `https://github.com/opensourceways/backlog/pull/55`）

## 核心理念
> 检视不是挑刺，是帮助团队提高交付质量。
> 关注"对不对"和"一致不一致"，不纠结风格偏好。
> 问题分级，让作者能快速判断优先级。

## 执行步骤

### 第一步：获取 PR 信息
1. 从参数中解析 PR 编号（纯数字默认为 `opensourceways/backlog`）
2. 使用 `gh pr view <number> --json title,body,files,additions,deletions,commits,url` 获取 PR 元信息
3. 使用 `gh pr diff <number>` 获取完整 diff
4. 记录：PR 标题、变更文件数、增删行数、提交数

### 第二步：理解变更上下文
1. 读取 `AGENTS.md` 了解仓库规范和标签体系
2. 根据 PR 关联的 Issue（从 PR body 中解析），使用 `gh issue view` 获取 Issue 信息
3. 如涉及 `opensourceways/issue_docs/{issueId}/` 下的文档，了解该 Issue 的需求背景

### 第三步：逐文件检视
按以下维度逐文件检查（不适用的维度跳过）：

#### A. Skill/命令文件（`.claude/commands/*.md`）
- 步骤是否完整、无歧义
- 参数说明是否清晰
- 是否与 AGENTS.md 中的规范一致
- 关键规范是否有遗漏

#### B. 规范文件（`AGENTS.md`、`README.md`）
- 仓库结构描述是否与实际目录一致
- 规范之间是否存在矛盾（如不同文件对同一事项的描述冲突）
- 引用的文件/路径是否真实存在

#### C. 需求分析说明书
- 文件名是否以 `#{issueId}` 开头
- 验收标准是否可量化、可测试
- 任务拆解是否紧凑（2-4 个 Task）
- 需求相关性分析勾选项是否给出理由
- 价值评估是否给出 Accept/Reject/Pending 结论
- 模板引导提示（`>` 引用块）和勾选项列表是否保留完整

#### D. 架构设计说明书
- 文件名是否以 `#{issueId}` 开头
- 目录名是否用 `Architecture Desgin`（保持历史拼写）
- `need_security` 时 3.1 安全设计是否已填写（威胁分析 + 安全设计实现 + 安全任务分解）
- 不涉及的章节是否保留结构并标注原因（而非删除）
- 模板引导提示是否保留

#### E. 测试策略/测试报告
- 文件标题和基本信息是否已替换（不能保留 `#1 [需求名称]` 模板占位符）
- 测试维度勾选是否与需求分析的标签一致
- `[TODO]` 字段是否按实际情况填写

#### F. 变更计划说明书
- 文件标题和基本信息是否已替换
- 变更等级、执行步骤、回滚方案是否按实际填写

#### G. 经验文件（`context/experience/*.md`）
- 经验是否具体可操作（有问题 → 原因 → 解决方案）
- 是否有正反示例

#### H. 交叉一致性检查
- 需求分析的标签结论 vs 实际创建的文档目录是否匹配
  - 未勾选 `need_itest` → 不应创建 Test 目录
  - 未勾选 `need_design` → 不应创建 Architecture Desgin 目录
- 交付件总结中引用的文件是否都真实存在
- 不同文件中对同一事项的描述是否一致

### 第四步：问题分级与整理

将发现的问题按以下等级分类：

| 等级 | 定义 | 处理要求 |
|------|------|----------|
| **高** | 内容错误、规范违反、文件间矛盾 | 必须修改后才能合入 |
| **中** | 可改进但不阻塞合入、表述不一致 | 建议修改，可在后续 PR 跟进 |
| **低** | 格式美化、[TODO] 跟进提醒 | 知晓即可 |

### 第五步：输出检视报告

按以下格式输出：

```
## PR #{number} 代码检视报告

**PR**: [标题](URL) | 变更文件数 | +增加/-删除
**关联 Issue**: #issueId

---

### 高优先级问题
1. **问题标题**
   - 文件：`file_path`
   - 问题描述
   - 建议修改方式

### 中优先级问题
（同上格式）

### 低优先级问题
（同上格式）

### 亮点
（值得肯定的地方，1-3 条）

---
### 检视结论
- [ ] **通过**：无高优先级问题
- [ ] **有条件通过**：高优先级问题修改后可合入
- [ ] **需要重新检视**：存在架构/方向性问题
```

### 第六步：提交检视评论（可选）

向用户确认是否将检视报告作为 PR 评论提交：
- 是 → 使用 `gh pr review <number> --comment --body "检视内容"` 提交
- 否 → 仅在终端输出

## 关键规范
- **就事论事**：指出具体问题和位置，不做笼统评价
- **给出建议**：每个问题附带修改建议或方向
- **认可亮点**：检视不只是找问题，好的设计和实践也要指出
- **尊重上下文**：理解需求背景再评判设计决策，避免脱离业务场景的教条式审查
- **规范优先**：以 AGENTS.md 和模板为检视标准，个人偏好不作为检视依据
