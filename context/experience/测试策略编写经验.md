# 测试策略编写经验

## 关键要点

### 1. 测试维度的勾选与标签对应

- `need_security` → 必勾选"安全与隐私测试"
- `need_itest` → 必勾选"集成测试"
- `need_design` → 可选勾选"集成测试"（取决于是否有跨组件）
- 功能测试通常总是勾选（强制执行）

### 2. 测试用例设计的粒度

- 每个测试用例对应架构设计中的一个TASK或SEC-TASK
- 用例数量不宜过多，3-5个用例/维度为宜
- 用例应包含：场景、预期结果、对应task链接

### 3. 安全测试的重点

- 凭证管理：硬编码检查、日志检查、Secret Store集成
- 数据加密：加密算法验证、密钥管理、完整性保护
- 访问控制：权限验证、未授权访问拒绝
- 日志脱敏：敏感信息过滤、日志内容审计
- 依赖漏洞：SBOM扫描、CVE检查

### 4. 集成测试的重点

- 端到端流程：从输入到输出的完整链路
- 多组件协作：各组件间的数据流转
- 错误处理：异常场景下的重试和恢复

### 5. 不涉及的测试维度

- 明确写出"不涉及，原因：xxx"
- 保留模板结构，不删除章节
- 测试报告中对应维度的用例数为0

### 6. 测试报告的占位符

- 测试报告使用[TODO]占位符
- 开发完成后填写实际测试结果
- 包含：预期结果、实际结果、证明截图

### 7. 测试通过标准的明确

- 所有功能测试用例通过
- 所有集成测试用例通过
- 所有安全测试用例通过
- 代码覆盖率要求（通常≥80%）
- 无高危安全漏洞

## 实践案例：Issue #178 统一账号服务删除账号验证码验证

### 测试策略特点

- **标签**：`need_security` + `need_design` + `need_itest` + `need_ux`
- **勾选维度**：功能测试、体验测试、集成测试、安全与隐私测试
- **不涉及**：可靠性、可服务性、性能（低频用户操作，非 Core 服务）

### 编写要点总结

#### 1. need_ux 触发体验测试时的重点

- 脱敏展示验证（联系方式不暴露原文）是核心体验+安全双重验证点
- UI 交互细节（倒计时、错误提示剩余次数）要独立成用例
- 体验测试用例不超过 3 个，聚焦关键交互节点

#### 2. 安全测试要与 SEC-TASK 一一对应

- 每个安全用例标注对应的 SEC-T 编号，确保设计闭环
- OTP 类需求的安全测试核心：脱敏、哈希存储、一次性使用、鉴权、越权

#### 3. 测试报告中不涉及的维度写法

- 汇总表中保留维度行，用例总数填 `-`，结论填 `N/A`
- 不删除行，保持表格结构完整

## 实践案例：Issue #67 LTS日志敏感信息扫描

### 测试策略特点

- **标签**：`need_security` + `need_design` + `need_itest`
- **勾选维度**：功能测试、集成测试、安全与隐私测试
- **不涉及**：体验测试、可靠性、可服务性、性能
- **实现语言**：Go（使用Kubernetes CronJob定时任务）

### 编写要点总结

#### 1. 功能测试的重新设计（6个TASK）

从功能架构层面完整对应TASK1-6，每个TASK一个主测试用例：

- **TASK1 - 扫描编排服务框架验证**
  - 定时任务按配置时间触发
  - CronJob创建Pod并执行扫描
  - 扫描完成后Pod自动清理
  - 异常情况下的重试机制

- **TASK2 - 凭证管理模块验证**
  - Pod启动时从Secret读取凭证
  - 凭证成功加载到内存
  - 配置文件启动后立即删除（覆写后删除）
  - 内存中的凭证可正常使用

- **TASK3 - 日志扫描器验证**
  - 扫描挂载目录中的日志文件
  - 准确过滤最近三天日志
  - 支持多云账号日志目录
  - 大文件正常处理

- **TASK4 - gitleaks敏感信息扫描验证**
  - AWS密钥、API Token、数据库凭证的准确检测
  - 正常日志无误报
  - 混合场景（部分敏感信息）的准确检测
  - 扫描结果JSON.GZ格式正确

- **TASK5 - 结果解析器验证**
  - 从扫描结果中准确提取namespace和pod信息
  - 添加时间戳等元数据
  - 缺失数据有默认值或标记
  - 生成结构化报告格式正确

- **TASK6 - 报告生成和加密验证**
  - 生成JSON格式的完整报告
  - 使用AES-256加密报告
  - 上传加密报告到OBS结果桶
  - 验证报告文件权限正确

#### 2. 集成测试的设计（4个场景）

从Kubernetes部署架构角度验证完整链路：

- **多云账号端到端流程验证**
  - 配置多个云账号（≥3个）的OBS日志桶
  - 各云账号日志目录通过NFS/S3挂载到Pod
  - 所有云账号日志均被成功扫描
  - 报告中能准确区分不同云账号的问题

- **Kubernetes部署和Pod生命周期验证**
  - CronJob按配置时间创建Pod
  - Pod以非Root用户运行（runAsUser > 1000）
  - Secret/ConfigMap正确挂载
  - Pod资源限制（CPU/Memory）有效
  - 扫描完成后Pod自动清理

- **凭证生命周期完整验证**
  - Pod启动时Secret中凭证配置文件可用
  - 凭证成功加载到内存
  - 内存凭证用于OBS连接
  - Pod执行过程中配置文件已删除
  - Pod退出时内存凭证释放

- **报告上传和存储验证**
  - 加密报告成功上传到OBS结果桶
  - 报告文件权限仅授权用户可访问
  - 加密报告无法被未授权用户读取
  - 授权用户可正确解密报告

#### 3. 安全测试的重新设计（7个维度）

对应6个SEC-TASK + 传输层安全：

- **凭证管理安全性验证（SEC-TASK1）**
  - 代码中无硬编码凭证
  - 日志中无凭证信息
  - 配置文件被安全删除（覆写后删除）
  - 内存中凭证受保护

- **报告加密和完整性验证（SEC-TASK2）**
  - 报告使用AES-256加密存储
  - 报告包含HMAC-SHA256签名
  - 篡改报告后签名验证失败
  - 使用正确密钥可成功解密

- **OBS结果桶访问控制验证（SEC-TASK3）**
  - 未授权用户访问被拒绝
  - 授权用户可成功读取报告
  - 报告文件权限为600或640
  - Object Lock设置有效

- **审计日志脱敏验证（SEC-TASK4）**
  - 审计日志不包含完整敏感信息
  - 日志仅包含操作类型和时间戳
  - 日志包含云账号ID但不包含凭证
  - 日志保留期设置为90天

- **容器安全策略验证（SEC-TASK5）**
  - 容器以非Root用户运行（UID > 1000）
  - 容器根文件系统为只读
  - CPU和内存限制已设置
  - 容器权限最小化

- **传输层安全验证**
  - 与OBS的通信使用TLS 1.2+
  - 日志下载使用HTTPS
  - 报告上传使用HTTPS

- **依赖漏洞扫描（SEC-TASK6）**
  - Go依赖包无高危CVE漏洞
  - gitleaks工具版本安全
  - 关键依赖定期更新

#### 4. 测试用例的结构化设计

每个测试用例都遵循统一的结构：

```
**N. 功能/集成/安全项名称验证**

* **对应task**: TASKX/SEC-TASKX - 任务描述
* **测试场景**:
  - 场景1
  - 场景2
  - 场景N
* **预期结果**:
  - 结果1
  - 结果2
  - 结果N
```

这样做的优点：

- 清晰关联架构设计中的TASK
- 便于追踪任务闭环
- 测试场景多角度验证
- 预期结果可量化

#### 5. 测试维度与需求标签的对应

根据需求分析阶段的标签勾选测试维度：

| 需求标签        | 必勾选维度     | 说明                   |
| --------------- | -------------- | ---------------------- |
| `need_security` | 安全与隐私测试 | 必须验证安全设计有效性 |
| `need_itest`    | 集成测试       | 必须验证端到端流程     |
| `need_design`   | 可选集成测试   | 如有跨组件则勾选       |
| 无特殊标签      | 功能测试       | 功能测试总是勾选       |

不涉及的维度应明确说明原因，而非删除章节。

#### 6. 测试执行计划的合理估算

基于测试用例数量和复杂度估算工作量：

| 测试阶段 | 测试类型   | 用例数 | 预计工作量 | 说明                     |
| -------- | ---------- | ------ | ---------- | ------------------------ |
| 单元测试 | 功能自检   | 6      | 3天        | 对应6个TASK              |
| 集成测试 | 集成测试   | 4      | 3天        | Kubernetes部署和完整流程 |
| 安全测试 | 安全与隐私 | 7      | 4天        | 对应6个SEC-TASK + 传输层 |
| 验收测试 | 全量验收   | 3      | 1天        | 冒烟测试和最终验收       |

关键因素：

- 安全测试通常耗时最长（涉及渗透和审计）
- 集成测试需要真实的Kubernetes环境
- 功能测试可由开发人员执行

#### 7. 测试报告的填写要点

- **基本信息**：需求链接、标签、责任人、时间
- **执行总体情况**：按维度统计通过率
- **缺陷统计**：高中低三个等级的数量和描述
- **详细记录**：每个用例的测试项、预期结果、实际结果、状态
- **问题记录**：发现的问题编号、描述、影响范围、修复状态
- **通过标准检查**：逐项验证是否满足
- **最终结论**：通过/有条件通过/未通过

#### 8. 常见错误和改进

**错误1：测试用例过多或过少**

- ❌ 每个维度超过10个用例 → 维度不清晰，验收困难
- ❌ 每个维度少于2个用例 → 覆盖不足
- ✅ 每个维度3-7个用例为合适范围

**错误2：用例未对应TASK**

- ❌ "验证系统运行正常"（模糊）
- ✅ "TASK1 - 扫描编排服务框架：验证定时任务按配置时间触发"（清晰）

**错误3：不涉及维度未说明原因**

- ❌ 直接删除不涉及的章节
- ✅ 保留章节，写"不涉及，原因：本需求是批处理任务，无需高可用"

**错误4：安全测试设计不全面**

- ❌ 只验证加密，忽视凭证管理和访问控制
- ✅ 覆盖STRIDE中的所有威胁类别

**错误5：测试报告只有[TODO]，未填写**

- ❌ 开发完成后仍然是占位符
- ✅ 每个用例都有实际的测试结果和证明截图

#### 9. 测试通过标准的明确化

建立清晰的通过标准，便于最终验收：

```
- ✅ 所有功能测试用例通过（6/6）
- ✅ 所有集成测试用例通过（4/4）
- ✅ 所有安全测试用例通过（7/7）
- ✅ 代码覆盖率 ≥ 80%
- ✅ 无高危安全漏洞
- ✅ 凭证管理安全性验证通过
- ✅ 审计日志脱敏验证通过
- ✅ 容器安全策略验证通过
- ✅ 依赖漏洞扫描通过
```

#### 10. 测试策略与架构设计的联动

好的测试策略应该是架构设计的"验收清单"：

- 架构设计中的每个TASK → 对应功能测试用例
- 架构设计中的每个SEC-TASK → 对应安全测试用例
- 架构设计中的部署架构 → 对应集成测试用例
- 不涉及的非功能设计 → 不涉及的测试维度

这样确保没有遗漏，也便于追踪TASK闭环。
