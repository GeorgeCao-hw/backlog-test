# 需求分析说明书编写经验

## 问题

第一次编写需求分析说明书时，容易遗漏需求相关性分析的勾选原因，或验收标准写得过于模糊。

## 关键要点

### 1. 验收标准必须可量化

- 错误示范："扫描工具可以正常工作"
- 正确示范："扫描覆盖率100%：服务开放清单中的所有服务均被扫描"
- 每条标准应包含：测量对象 + 测量方法 + 合格阈值

### 2. 需求相关性分析要给出理由

- 勾选项必须写明原因（模板中有明确要求）
- 未勾选项如有争议，也建议写明排除理由
- 安全相关性分析（A环节）的结论会向下传导影响 B/C 环节

### 3. 任务拆解要紧凑实际

- Task 数量控制在 **2-4 个**，不宜太散
- 合并相关性强的工作（如核心逻辑 + 报告生成合为一个 Task）
- 不要把测试、文档单独拆成独立 Task，应包含在对应功能 Task 的工作量中
- 工作量贴合实际，不要虚报

### 4. 文字精简，只做简要分析

- 需求分析说明书**不做具体设计**，具体设计留给架构设计文档
- 场景说明 2-3 句话，验收标准每条一句话
- 核心逻辑方案 3-5 句话概述思路即可
- 相关性分析勾选原因一句话说清

### 5. 文件命名用 Issue 编号

- 文件名以 `#{issueId}` 开头（如 `#29 Requirement Analysis Specification.md`）
- 不是固定的 `#1`，每个 Issue 用自己的编号

### 6. 需求范围要明确边界

- 明确写出"本次需求范围"
- 同时写出"不在本次需求范围内"的内容
- 避免范围蔓延

### 7. 保留模板自带的引导提示

- 模板中的 `>` 引用块（如 `> 描述"在什么情况下..."`、`> 操作说明：...`）必须保留
- 相关性分析的完整勾选项列表必须保留，即使未勾选也不能删除
- 价值评估表格的完整维度和评估问题列必须保留
- 只填写内容，不删除模板结构

### 8. Issue 描述信息不足时的处理

- 当【需求详情】为空或过于简短时，从【需求背景】和【需求价值】推断
- 验收标准仍需具体可量化，不能因为 Issue 描述简短就写得模糊
- 如信息严重不足影响判断，应提示用户补充 Issue 详情

### 9. 按需创建目录，不预创建模板

- 需求分析只产出需求分析说明书，不复制架构设计/测试/变更计划模板
- 根据标签结果提示用户是否进行下一步（架构设计、测试策略等）
- 用户确认后再按需创建对应目录和模板文件

### 10. 安全类需求的特殊注意

- 扫描类工具发起 HTTP 探测算"边界变更"，涉及网络访问行为
- 即使工具本身不暴露接口，安全设计仍然必要（扫描报告本身是敏感信息）
- "首次全量扫描"可作为独立 Task（一次性工作 + 独立交付件）

### 11. 需求相关性分析中标签勾选的逻辑一致性 ⚠️ 常见坑点

**问题场景**：A/B/C 环节各项勾选与 5.1 汇总结果不一致

**常见错误示范**：

- 问题 1：A 环节勾选了"凭证处理"，但 5.1 汇总结果仍勾选 `need_light`（轻量化）
- 问题 2：C 环节文字说明已识别"跨组件影响""端到端流程"，但勾选项未勾选，导致 `need_itest` 未触发
- 问题 3：A 环节触发了 `need_security`，但 B 环节第一项"A 环节判定需要完成安全设计"未勾选

**标签体系的传导逻辑**：

1. **A 环节任一项勾选** → 必须在 5.1 勾选对应标签
   - A 的凭证/权限/隐私/AI → `need_security` → 自动触发 `need_design`
   - A 的边界变更 → `need_security`
2. **B 环节第一项** 必须与 A 的结论联动
   - 若 A 环节触发 `need_security`，则 B 第一项必勾选 `[x] A环节判定需要完成安全设计`
3. **C 环节的联动** 要检查实际是否存在跨组件或端到端流程
   - trigger → issue 两个模块间有数据依赖 = 跨组件影响
   - SBOM 扫描 → 包信息 → CVE 匹配 → issue 创建 = 端到端流程
4. **5.1 汇总必须是 A/B/C 的综合结论**
   - 若 A 勾选凭证处理 + C 勾选跨组件+端到端 → 5.1 应为 `need_security` + `need_design` + `need_itest`
   - 决不能因为"主要是配置变更"就勾选 `need_light`

**检查清单**：

- [ ] A 环节每一项勾选都在 5.1 中有对应标签
- [ ] B 环节第一项与 A 结论一致
- [ ] C 环节的文字说明与勾选项一致
- [ ] 5.1 汇总结果是否遗漏了任何应勾选的标签
- [ ] `need_light` 仅在 A/B/C 全部未勾选时才能勾选

## 标签判定速查

- 涉及安全 6 项中任一 → `need_security` → 自动触发 `need_design`
- 涉及架构 4 项中任一 → `need_design`
- 涉及测试 5 项中任一 → `need_itest`
- 涉及UX 4 项中任一 → `need_ux`
- 以上全部未勾选 → `need_light`

## 实践案例：Issue #67 LTS日志敏感信息扫描

### 需求特点

- **类型**：安全扫描工具类需求
- **复杂度**：中等（涉及多云账号、凭证管理、数据加密）
- **标签结论**：`need_security` + `need_design` + `need_itest`

### 编写要点总结

#### 1. 安全扫描类需求的相关性分析

- **凭证处理**：OBS AK/SK 的安全存储和使用是核心安全风险
- **隐私风险**：扫描结果本身包含敏感信息（密钥、Token等），需要加密存储和访问控制
- **这两项勾选自动触发** `need_security` 和 `need_design`

#### 2. 任务拆解的粒度

- 本需求拆解为 3 个 Task（紧凑实际）
- Task1：OBS连接和日志下载（包含多云账号支持）
- Task2：gitleaks集成和结果解析
- Task3：报告生成和上传
- 避免过度拆解，相关性强的工作合并

#### 3. 验收标准的量化

- "扫描覆盖率100%"：明确了测量对象和阈值
- "检测准确率"：与预期敏感信息类型一致
- "结果可追踪性"：能定位到namespace和pod
- 每条标准都是可测试的

#### 4. 范围边界的明确

- **在范围内**：定期扫描、敏感信息检测、结果定位
- **不在范围内**：自动修复、修改应用日志、跨云账号聚合展示
- 避免需求蔓延

#### 5. 相关性分析的逻辑一致性

- A环节勾选"凭证处理"和"隐私风险" → `need_security`
- B环节第一项自动勾选（A环节触发）→ `need_design`
- C环节勾选"上述环节判定需要执行安全设计" → `need_itest`
- 5.1汇总结果与各环节勾选项完全对应

## 实践案例：Issue #178 统一账号服务删除账号增加验证码验证

### 需求特点

- **类型**：账号安全加固类需求（增加操作验证环节）
- **复杂度**：中等（前后端均有改动，涉及OTP凭证处理和隐私数据）
- **标签结论**：`need_security` + `need_design` + `need_itest` + `need_ux`

### 编写要点总结

#### 1. 安全类需求中"凭证处理"的判断

- OTP 验证码本质是一次性凭证（需存储、有有效期、有使用次数限制），属于"凭证处理"
- 不应局限于"长期密钥/证书"，一次性 Token 也符合凭证处理的定义

#### 2. 同时触发多个标签时的联动检查

- A 环节勾选凭证处理 + 隐私风险 → `need_security` → B 第一项必须自动勾选 → `need_design`
- C 环节"上述环节"+ "端到端流程" 均勾选 → `need_itest`
- D 环节前端交互变更 → `need_ux`
- 4 个标签同时触发时，确保 5.1 汇总不遗漏任何一项

#### 3. 账号安全类需求的范围边界

- **在范围内**：验证环节本身（发送OTP、校验OTP、失败锁定）
- **不在范围内**：账号注销的下游逻辑（数据清理、第三方解绑）、新增绑定渠道
- 要明确排除"修改现有删除业务逻辑"，避免范围蔓延

#### 4. Issue 描述极简时的验收标准写法

- Issue 仅提供一句话背景时，需从安全最佳实践补充具体可量化标准
- 如：OTP 有效期（5分钟）、错误次数限制（3次）、一次性使用限制等都属于合理补充

## 实践案例：Issue #114 MinsdSpore-移除MindSpore用户名回调

### 需求特点

- **类型**：集成清理/技术债务类需求（移除废弃回调）
- **复杂度**：低（纯代码删除 + 配置清理）
- **标签结论**：`need_light`

### 编写要点总结

#### 1. 清理类需求的隐私风险判断（常见误判）

- **错误思路**：移除用户注册/删除回调 → 涉及用户账号数据 → 勾选隐私风险评估
- **正确判断**：移除回调**不改变个人数据处理方式**，只是删除了一条外部调用路径，不触发 `need_security`
- **判断原则**：隐私风险评估的触发条件是"改变个人数据的处理逻辑"，纯移除不构成新的数据处理

#### 2. Issue 描述极简时的处理

- Issue 只有一句话描述时，从标题推断业务背景
- 验收标准仍要具体（如"通过网络抓包或日志确认无回调请求"）
- 范围边界要明确写出"不在范围内"（如 MindSpore 侧数据清理）

#### 3. 任务拆解：移除类需求 2 个 Task 即可

- TASK1：移除回调代码（含单测）
- TASK2：清理相关配置
- 不需要额外的测试 Task（已包含在 TASK1 工作量中）

## 实践案例：Issue #148 GitHub CI Workflow 指标采集

### 需求特点

- **类型**：数据采集工具类需求
- **复杂度**：中等（多仓库、step映射、device映射、增量更新）
- **标签结论**：`need_db` + `need_arch`

### 编写要点总结

#### 1. Task 数量控制

- 初稿拆解为 6 个 Task，过于分散
- 按指南合并为 3 个：数据模型+采集逻辑、表定义+聚合、测试+配置
- 相关性强的工作合并，测试/配置不独立拆分

#### 2. 范围边界必须明确

- 需要明确写出"不在本次需求范围内"的内容
- 本例排除：CI数据可视化、自动优化建议、跨仓库对比

#### 3. 价值评估章节不可省略

- 必须给出 Accept/Reject/Pending 结论
- 评估维度：业务价值、技术可行性、资源投入

#### 4. Mermaid 流程图简化

- 核心逻辑方案用简化流程图展示（6个节点足够）
- 不需要完整详细流程，具体设计留给架构文档
