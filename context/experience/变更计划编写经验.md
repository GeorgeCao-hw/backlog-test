# 变更计划说明书编写经验

## 关键要点

### 1. 变更等级判定
- **L1 (重大)**：数据库 Schema 修改、全局配置中心变更、底层网络拓扑调整
- **L2 (普通)**：微服务配置变更、非核心插件发布、新开发服务上线
- **L3 (轻微)**：代码删除/清理、Bug修复、不影响逻辑的配置微调

代码删除类需求（如移除废弃集成）通常为 **L3**。

### 2. 变更内容章节
模板中无此章节，但推荐为删除/修改类变更补充"变更内容"表格，列出：
- 删除/修改的文件路径
- 每个变更的说明

新增类变更还应列出新增文件、数据库表结构等。

### 3. 删除类变更的回滚方案
- 删除代码的回滚通常只需一步：`kubectl rollout undo` 或重新部署旧镜像
- 注意说明：回滚后对数据的影响（如本案例：回滚后回调会重新生效，不影响已有数据）

### 4. 生产验证要具体可操作
- 不要写"验证功能正常"这种模糊描述
- 删除回调场景：明确"执行注册/删除操作，检查日志确认无回调记录"
- 能给出具体日志关键词、SQL 语句、curl 命令更好

### 5. 文件命名
- 格式：`#{issueId} {变更简述} Change Plan Specification.md`
- 示例：`#114 MindSpore Callback Removal Change Plan Specification.md`

## 实践案例：Issue #178 统一账号服务删除账号验证码验证

- **类型**：新功能上线（新增接口 + 修改已有接口逻辑）
- **变更等级**：L2（普通）
- **执行步骤**：4步（后端发布 → 前端发布 → 线上观测 → 功能验证）
- **回滚方案**：3步（后端回滚 → 前端回滚 → 验证回滚）
- **特点**：need_security 需求，关联测试报告；Redis 残留 OTP Key 无需手动清理（TTL 自动过期）

### 关键经验

#### 1. 新功能上线通常定级 L2
- 新增接口 + 修改已有接口逻辑 = L2（普通）
- 无数据库 Schema 变更、无网络拓扑调整，不需升为 L1

#### 2. 前置条件检查清单很重要
- 上线前明确检查：测试用例全通过、依赖服务（Redis/通知服务）可用
- 将依赖服务的连通性确认列为前置条件，避免上线后发现依赖不可用

#### 3. 临时状态数据的回滚说明
- Redis 中的 OTP Key 有 TTL，回滚后无需手动清理
- 要明确说明"回滚后无副作用"，消除操作者顾虑

#### 4. 生产验证要覆盖正常+异常路径
- 正常路径：完整的 OTP 发送→验证→删除端到端流程
- 异常路径：不携带 OTP 直接调用删除接口（验证安全拦截生效）

## 实践案例：Issue #114 移除MindSpore用户名回调

- **类型**：代码删除 + 配置清理
- **变更等级**：L3（轻微）
- **执行步骤**：3步（代码合入 → 测试环境验证 → 生产发布）
- **回滚方案**：单步 kubectl rollout undo
- **特点**：need_light 需求，无关联测试报告
