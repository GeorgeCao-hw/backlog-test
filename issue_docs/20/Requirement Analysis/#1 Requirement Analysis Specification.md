## 2. 需求场景说明

> 描述"在什么情况下，为了解决什么问题，用户需要做什么"。

**场景说明:**

门禁系统在执行完成后，需要通知开发者门禁结果。由于门禁结果日志包含安全相关信息（如代码路径、内部配置等），不适合通过公开访问方式查看，需要通过邮件方式主动通知开发者。

门禁系统需要根据代码提交者的 github id 或 gitcode id 获取对应的邮箱地址，但目前缺少统一的数据获取渠道。

**本次需求范围**：数据中台基于现有的社区用户数据，提供标准化的 API 接口，供门禁系统（及未来其他系统）查询 github id、gitcode id 对应的邮箱地址。

**注**：门禁系统的邮件通知功能不在本次需求范围内，由门禁系统后续自行实现。

## 3 需求验收标准

> 明确需求完成的标志，必须是可量化、可测试的。

**验收标准:**

- 数据中台成功提供 RESTful API 接口，支持通过 github id 或 gitcode id 查询邮箱地址
- API 接口查询成功率 ≥ 99%（对于数据中台已有的用户数据）
- API 接口响应时间 P95 ≤ 500ms
- API 接口提供完善的错误码和错误信息（如：用户不存在、邮箱未绑定、参数错误等）
- API 访问需要有认证机制（API Key 或 Token），保障数据安全
- 提供 API 接口文档（包含接口路径、请求参数、响应格式、错误码说明、使用示例等）
- API 访问日志记录完整，可用于审计和问题排查
- 提供监控告警，当 API 可用性低于 99% 或响应时间超过阈值时触发告警

## 4. 需求设计与分解

> 说明：基于初步方案，将需求拆解为可实施的原子 Task。后续的流程判定将严格依据这些 Task 的影响范围进行。

### 4.1 核心逻辑方案

> 简述实现逻辑（如：数据流向、模块改动、新增配置项等），作为任务拆解的理论依据。图片文字形式不限。

**逻辑方案:**

1. **数据源确认**：
   - 确认数据中台现有用户数据库中是否包含 github id、gitcode id、email 的映射关系
   - 如数据不完整，需要评估数据补全方案（不在本次需求范围）

2. **API 接口设计**：
   - 提供 RESTful API 接口：`GET /api/v1/users/email`
   - 支持查询参数：`github_id` 或 `gitcode_id`（二选一，优先使用提供的参数）
   - 响应格式（成功）：
     ```json
     {
       "code": 200,
       "message": "success",
       "data": {
         "email": "user@example.com",
         "github_id": "xxx",
         "gitcode_id": "xxx"
       }
     }
     ```
   - 响应格式（失败）：
     ```json
     {
       "code": 404,
       "message": "User not found",
       "data": null
     }
     ```

3. **认证机制**：
   - API Key 方式：调用方在请求头中携带 `X-API-Key`
   - API Key 管理：支持生成、撤销、续期
   - 访问权限控制：限制不同 API Key 的访问频率和范围

4. **日志与监控**：
   - 记录所有 API 访问日志（请求参数、响应结果、调用方、时间戳等）
   - 日志脱敏：敏感信息（邮箱）需要脱敏处理
   - 监控指标：QPS、响应时间、成功率、错误率等
   - 告警规则：可用性 < 99%、响应时间 P95 > 500ms

5. **数据流向**：
   门禁系统（或其他调用方） → API 网关（认证） → 数据中台 API 服务 → 用户数据库 → 返回邮箱信息
