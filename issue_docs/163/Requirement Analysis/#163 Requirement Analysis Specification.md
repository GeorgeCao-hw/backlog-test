## 2. 需求场景说明

vllm相关issue已采集到内部数据库（表名：`fact_vllm_issue`），但缺乏系统化的分类机制，影响数据统计、报表生成和问题分析。

1. **数据统计场景**：社区管理员需要按类型（咨询、需求、缺陷、公告等）统计vllm issue，了解不同类型问题的分布情况
2. **报表生成场景**：运营团队需要基于issue类型生成各类分析报表，如缺陷趋势、需求优先级等
3. **问题分析场景**：开发者需要按问题类型筛选和定位issue，提高问题处理效率
4. **配置管理场景**：系统管理员需要动态调整分类规则，适应不同社区的标签体系

**现有分类器分析：**
- **通用分类器**：`issue_type_cleaning_rule.py`（咨询/需求/缺陷） - 基于issue_type字段
- **ascend分类器**：`label_issue_type_cleaning_rule.py`（咨询/需求/缺陷/公告/特殊/未归类） - 基于标签+标题+issue_type
- **opengauss分类器**：`label_issue_type_v2_cleaning_rule.py`（咨询/问题/缺陷/需求/未分类） - 简化版分类器

## 3. 需求验收标准

- [ ] **数据库配置表**：创建`issue_classification_rule`表，支持动态配置分类规则
- [ ] **通用分类器**：实现`ConfigurableIssueTypeCleaningRule`，支持按社区配置不同规则
- [ ] **VLLM分类器**：实现`ConfigurableIssueTypeCleaningRuleVLLM`子类，针对vllm社区进行分类
- [ ] **分类逻辑**：支持三层匹配优先级（标签→标题→issue_type），与ascend分类器一致
- [ ] **分类类型**：采用ascend的6类分类（咨询、需求、缺陷、公告、特殊、未归类）
- [ ] **规则变更**：规则配置变更后，已分类记录不自动更新（与IssueTypeCleaningRule一致）
- [ ] **标题匹配**：使用严格前缀匹配（startswith），而非包含匹配
- [ ] **测试覆盖**：单元测试覆盖所有分类逻辑，集成测试验证完整清洗流程
- [ ] **文档完整**：设计文档、使用说明、配置管理文档齐全

## 4. 需求设计与分解

### 4.1 核心逻辑方案

1. **数据库层**：
   - 创建`issue_classification_rule`配置表，存储标签到分类的映射规则
   - 支持按社区（community）配置不同规则，支持通配符匹配
   - 规则包含类型（label/title/issue_type）、模式（pattern）、分类（category）、优先级（priority）

2. **清洗规则层**：
   - 实现`ConfigurableIssueTypeCleaningRule`基类，继承`CleaningRule`
   - 从数据库加载规则，实现标签匹配、标题前缀匹配、issue_type模糊匹配
   - 支持缓存机制，提高规则匹配性能

3. **数据流**：
   - 输入：`fact_vllm_issue`表中的issue数据（包含标签、标题、issue_type）
   - 处理：按优先级匹配规则（标签→标题→issue_type）
   - 输出：更新`dws_vllm_contribute`表中的`super_issue_type`字段
