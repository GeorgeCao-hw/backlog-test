## 3. 生产环境验证

> **参考方向**：变更后如何快速确认"系统是好的"且功能符合预期。

**验证方式：**

**核心接口拨测**：调用 `POST /api/v1/account/delete/send-otp`（使用测试账号），确认返回 200 且通知服务正常发送验证码至测试邮箱/手机。

**日志特征匹配**：检查账号服务日志，确认以下特征：
- 存在 OTP 发送成功的 INFO 日志，且日志中**无 OTP 明文**（应为 `***`）
- 无新增 ERROR 堆栈
- Redis 操作（SET/DEL）日志正常

**功能闭环验证**：使用专用测试账号执行完整删除流程，确认：
- 验证码发送成功（邮箱/手机均测试）
- OTP 正确时账号删除成功
- OTP 错误 3 次后操作锁定

**异常场景抽测**：不携带 OTP 直接调用删除接口，确认返回 400 而非执行删除。

## 4. 回滚方案

> **原则**：回滚必须是受控且经过验证的，**禁止现场临时拼凑命令**。

> 出现以下任意一种情况，必须立即中断变更并启动回滚：
> 1. **指标异常**：错误率超过 5% 或 P99 延迟增加超过 50% 且持续 2 分钟。
> 2. **核心阻塞**：主要业务链路中断，且无法在 10 分钟内定位根因。
> 3. **不可抗力**：变更期间发生严重的云服务中断或网络分区。

> 参考：
> * **代码/版本回滚**：执行 `kubectl rollout undo` 命令或重新部署上一个稳定版本的镜像。
> * **配置回滚**：将配置中心（如 Nacos/Apollo）切换回上一个版本的快照。
> * **数据回滚**：执行数据库倒滚脚本或恢复快照（注意数据一致性评估）。

**回滚说明**：本次变更为新增接口 + 修改删除接口逻辑，回滚即恢复旧版本镜像。回滚后删除账号接口恢复原有逻辑（仅需二次确认），无数据库 Schema 变更，无需数据回滚。Redis 中残留的 OTP Key 会在 TTL 到期后自动清除，无需手动处理。

**回滚执行路径：**

| 步骤     | 回滚动作   | 执行命令/方式                                                                    | 预期结果                             |
|--------|--------|----------------------------------------------------------------------------|----------------------------------|
| **R1** | 后端版本回退 | `kubectl rollout undo deployment/<account-service-deployment>` | 账号服务恢复至上一个稳定版本，删除接口恢复原有逻辑。       |
| **R2** | 前端版本回退 | 通过 CI/CD 流水线重新发布上一个前端稳定版本。                                                | 前端页面恢复，验证码交互入口消失，删除账号流程恢复原样。     |
| **R3** | 验证回滚结果 | 访问删除账号页面，确认无验证码输入步骤，并使用测试账号执行一次原删除流程（仅需二次确认弹窗）。                           | 删除流程恢复正常，服务无异常报错，错误率回落至基线水平。 |
