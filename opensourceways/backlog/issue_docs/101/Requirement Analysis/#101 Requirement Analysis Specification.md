## 2. 需求场景说明

### 2.1 论坛负向事件识别

在社区论坛运营过程中，需要识别和监控负向事件帖子，包括投诉反馈、问题求助、安全风险、负面情绪、争议讨论五类。通过关键词规则匹配，对主题帖进行评分，输出风险等级（P0-P4），帮助运营团队及时发现和处理潜在问题。

**数据范围:**
- 输入表: `fact_{community}_forum_topic` (主题帖) + `fact_{community}_forum_post` (回复帖)
- 输出表: `dwm_{community}_forum_negative_event` (负向事件评分表)

**数据获取说明:**
负向事件的判定维度是 Topic，但在判断一个 Topic 是否是负向事件时，需要综合分析：
1. Topic 的 `title` 字段（标题）
2. 该 Topic 下所有 Post 的 `excerpt` 字段（内容/摘要）

### 2.2 Issue严重缺陷识别

从GitHub Issue数据中识别严重缺陷，包括CVE漏洞、安全问题、服务崩溃、死锁阻塞、内存问题等。通过关键词规则、优先级、标签等多维度评分，输出严重度等级，帮助技术团队及时发现和处理严重问题。

**数据范围:**
- 输入表: `fact_{community}_issue` (Issue数据)
- 输出表: `dwm_{community}_issue_defect` (严重缺陷评分表)

## 4. 需求设计与分解

### 4.1 论坛负向事件识别逻辑方案

1. **数据获取**: 从 `fact_{community}_forum_topic` 获取主题帖数据，同时获取该 Topic 下所有 `fact_{community}_forum_post` 数据
2. **删除数据检查**: 查询源表时检查 `is_removed` 字段，对已删除的源数据（`is_removed = true`），删除输出表中对应记录
3. **排除检查**: category_name 包含"公告"、"通知"的帖子不参与评价
4. **询问性质检测**: 检测是否包含询问性质关键词（是否、有没有、如何、怎么等）
5. **确认性检测**: 检测是否包含确认性关键词（发现、遇到、出现、确认等）
6. **关键词匹配**: 对 Topic 的 `title` 以及所有 Post 的 `excerpt` 进行关键词匹配
   - 标题关键词命中: 20分 × 权重
   - Post内容关键词命中: 10分 × 权重
7. **评分调整**:
   - 询问性质帖子（无确认词）: 分数降低70%
   - 有确认词（非询问）: 加分
   - 情绪强度加分: 感叹号数量、重复负面词
8. **等级划分**: P0-P4 五档风险等级
9. **结果存储**: 写入 `dwm_{community}_forum_negative_event` 表

**处理模式说明:**

| 模式 | 参数 | 处理方式 |
|------|------|---------|
| 全量 | `--mode full` | 处理所有历史数据，输出表先清空再写入 |
| 增量 | `--mode incremental --incremental-days N` | 处理脚本运行时间的前N天至今的数据，使用 upsert 更新 |

**五类负向事件及基础分:**

| 编码 | 名称 | 基础分 |
|------|------|--------|
| COMPLAINT | 投诉反馈 | 70 |
| HELP_REQUEST | 问题求助 | 30 |
| SECURITY | 安全风险 | 90 |
| NEGATIVE_EMOTION | 负面情绪 | 50 |
| CONTROVERSY | 争议讨论 | 45 |

### 4.2 Issue严重缺陷识别逻辑方案

1. **数据获取**: 从 `fact_{community}_issue` 获取Issue数据
2. **删除数据检查**: 查询源表时检查 `is_removed` 字段，对已删除的源数据（`is_removed = '1'`），删除输出表中对应记录
3. **非缺陷类型检测**: 检测是否为需求、建议、文档、任务等非缺陷类型
4. **外部引用检测**: 检测是否引用外部项目/新闻（非本项目问题）
5. **询问性质检测**: 检测询问性质关键词
6. **关键词匹配**: 对 title、body、labels_name 字段进行匹配
   - 标题关键词: 各关键词独立权重（如 CVE-: 45, crash: 30）
   - 正文关键词: 各关键词独立权重
   - 标签关键词: 如 security: 30, critical: 25
7. **优先级权重**: P4=25, P3=15, P2=8, P1=0, P0=0
8. **issue_type权重**: bug: 8, security: 20
9. **security_hole字段**: 35分
10. **CVE优先级调整**:
    - 优先级 0/1: 降分90%
    - 优先级 3: 加分20%
    - 优先级 4: 加分50%
11. **等级划分**: 极严重(≥60)、严重(40-59)、中等(25-39)、轻微(10-24)、正常(<10)
12. **结果存储**: 写入 `dwm_{community}_issue_defect` 表

**处理模式说明:**

| 模式 | 参数 | 处理方式 |
|------|------|---------|
| 全量 | `--mode full` | 处理所有历史数据，输出表先清空再写入 |
| 增量 | `--mode incremental --incremental-days N` | 处理脚本运行时间的前N天至今的数据，使用 upsert 更新 |

**多代码平台支持:**

由于同一社区可能在多个代码平台（gitee、gitcode、github）上创建 Issue，Issue ID 可能重复。因此：
- 输出表增加 `code_platform` 字段
- 主键 `uuid` 格式调整为：`{community}-{code_platform}-{issue_id}`

**缺陷分类:**
- CVE漏洞、安全问题、服务崩溃、死锁/阻塞、内存问题、数据问题、性能问题、功能缺陷、兼容性

* [ ] **凭证处理**：涉及密钥（Secret/Key）、Token、证书的存储或分发。
* [ ] **权限调整**：修改权限模型、服务账号（SA）权限或鉴权逻辑。
* [ ] **供应链**：引入新的第三方二进制文件、SDK 或重大版本依赖升级。
* [ ] **隐私风险评估**：涉及用户个人数据（Email、手机号、IP、邮箱 等）的处理。
