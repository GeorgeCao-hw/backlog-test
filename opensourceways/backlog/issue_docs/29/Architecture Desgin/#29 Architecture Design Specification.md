**设计说明/归档：**

系统由以下核心组件构成：

```
+------------------+     +------------------+     +------------------+
| 服务清单解析模块  | --> | Swagger端点探测模块| --> | 报告生成模块      |
| (ServiceParser)  |     | (SwaggerProber)  |     | (ReportGenerator)|
+------------------+     +------------------+     +------------------+
                                                          |
+------------------+     +------------------+              v
| 定时调度模块      | --> | 增量对比&告警模块 | <-- | 历史报告存储      |
| (CronScheduler)  |     | (DiffAlerter)    |     | (ReportStore)    |
+------------------+     +------------------+     +------------------+
```

**流程说明**：
1. ServiceParser 读取服务开放清单，解析出目标服务地址列表
2. SwaggerProber 对每个地址并发探测预定义的 Swagger 路径集合
3. ReportGenerator 汇总探测结果生成结构化报告（JSON/Markdown）
4. CronScheduler 定时触发扫描，DiffAlerter 对比历史报告输出增量告警

### 2.3 组件职责与接口

> 列出新增/修改的组件及其定义的 API 规范。**不涉及需要说明原因**

**设计说明/归档：**

| 组件 | 职责 | 输入/输出 |
|------|------|----------|
| **ServiceParser** | 解析服务开放清单，输出目标地址列表 | 输入：配置文件路径；输出：`List[ServiceTarget]` |
| **SwaggerProber** | 对单个服务探测所有预定义 Swagger 路径 | 输入：`ServiceTarget`；输出：`List[ProbeResult]` |
| **ReportGenerator** | 汇总探测结果，生成结构化报告 | 输入：`List[ProbeResult]`；输出：Markdown/JSON 报告文件 |
| **DiffAlerter** | 对比本次与上次报告，识别新增暴露 | 输入：本次报告 + 历史报告；输出：增量告警消息 |
| **CronScheduler** | 定时触发扫描任务 | 输入：cron 表达式；输出：触发扫描流程 |

预定义 Swagger 探测路径集合：
- `/swagger-ui.html`
- `/swagger-ui/index.html`
- `/v2/api-docs`
- `/v3/api-docs`
- `/swagger-resources`
- `/doc.html`（Knife4j）

判定逻辑：HTTP 状态码 200 且响应体包含 Swagger 特征关键字（如 `"swagger"`, `"openapi"`, `"ApiOperation"`）。

### 3.1.2 安全设计实现 (Security Mechanisms)

> **参考：**
> 威胁模型评估：
> * 是否已根据业务逻辑绘制 Data Flow Diagram 并识别单点风险？
>
> 软件供应链：
>* 是否扫描并修补了已知漏洞（CVE）？
>* 是否限制了第三方二进制包的直接引入？
>*
>凭证管理：
>* 严禁硬编码。
>* 密钥是否定期自动轮转（Rotation）？
>
>身份认证：
>* 是否具备多因素认证支持或联邦认证（OIDC）对接能力？
>* 内部微服务调用是否执行了身份校验（Identity-based Auth）？
>
>数据安全：
>* 传输加密（TLS 1.2+）与静态加密（AES-128）是否全覆盖？
>* 是否对高敏感字段（如手机号、秘钥）执行了哈希/加盐或差分隐私处理？
>
>运行时隔离：
>* 容器是否以非 Root 用户运行（Non-root Enforcement）？
>* 是否配置了 Read-only Root Filesystem 防止二进制篡改？
>
>日志审计：
>* 关键操作日志是否具备防篡改性？
>* 是否包含了足够用于追溯的 4W 信息（Who, When, Where, What）？

**设计说明/归档：**

* **报告访问控制**：扫描报告存储在内部仓库，文件权限限制为团队成员只读，不推送到公开仓库。
* **请求安全**：扫描请求仅使用 HTTP GET，不携带认证凭证，不修改目标服务状态。探测使用 HTTPS 优先。
* **日志脱敏**：日志仅记录服务名、端点路径、状态码，不记录响应体内容，避免泄露 API 结构详情。
* **并发控制**：默认并发数限制为 5，单个请求超时 10 秒，请求间随机延迟 0.5-1 秒，避免对目标服务造成压力。
* **供应链**：仅依赖标准 HTTP 库（如 Python requests），不引入额外第三方二进制包。
* **运行时**：以非 Root 用户运行，扫描脚本本身无持久化存储需求。
