## 2. 需求场景说明

> 描述"在什么情况下，为了解决什么问题，用户需要做什么"。

**场景说明:**

cve-manager-ng 作为社区 CVE 扫描管理服务，当前存在三项需要优化的问题：

1. **SBOM 扫描磁盘占用过高**：服务在扫描仓库 SBOM（软件物料清单）信息时，磁盘利用率异常升高，存在磁盘耗尽导致服务中断的风险。需要优化扫描逻辑，控制磁盘占用（如流式处理、及时清理扫描临时文件等）。

2. **Gitee 遗留逻辑待清理**：ascend、cann 项目已完成从 Gitee 到 GitHub 的迁移，服务中仍保留了历史遗留的 Gitee 相关逻辑（API 调用、配置项、鉴权引用等），增加了代码维护成本和潜在的安全攻击面，需在迁移确认完成后予以移除。

3. **cann 引导评论体验不佳**：cve-manager-ng 在 cann 仓库触发的自动引导评论内容待优化，当前评论表述不清晰，影响贡献者对修复流程的理解与跟进效率。

## 3. 需求验收标准

> 明确需求完成的标志，必须是可量化、可测试的。

**验收标准:**

- SBOM 扫描过程中磁盘峰值使用量相比优化前显著下降，扫描结束后临时文件已清理，磁盘使用率恢复至正常水位。
- 代码库中所有 Gitee 相关逻辑（API 调用、配置项、凭证引用）已全部移除，服务在 GitHub 侧功能验证正常，无回归问题。
- cann 仓库的引导评论内容经评审确认表述清晰，贡献者可依据评论内容独立完成修复流程，无歧义。

## 4. 需求设计与分解

> 说明：基于初步方案，将需求拆解为可实施的原子 Task。后续的流程判定将严格依据这些 Task 的影响范围进行。

### 4.1 核心逻辑方案

**逻辑方案:**

- **TASK1（SBOM 优化）**：分析当前扫描流程中磁盘占用高的根因（如：全量克隆仓库后未及时清理、扫描产物未限制大小等），改为浅克隆或流式扫描，并在扫描完成后及时删除本地临时目录，从而将磁盘使用量控制在合理范围。

- **TASK2（移除 Gitee 逻辑）**：梳理并移除服务中所有依赖 Gitee 的逻辑，包括：Gitee API 调用封装、Gitee Token/Secret 引用、Gitee 相关配置项及分支判断逻辑。移除前需确认 ascend、cann 仓库迁移已完成且 Gitee 侧无活跃 webhook/CI 依赖。

- **TASK3（优化 cann 引导评论）**：梳理 cann 仓库当前的自动评论模板，结合实际修复流程重新撰写引导内容，确保步骤清晰、链接有效、语义无歧义。
