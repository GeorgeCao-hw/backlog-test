## 2. 需求场景说明

> 描述"在什么情况下，为了解决什么问题，用户需要做什么"。

**场景说明:**

当前openGauss社区运营质量需要提升，社区运营人员需要通过看板总览快速了解社区运营状态。具体场景包括：

1. **Issue响应监控场景**：SIG组维护者需要了解各自负责的Issue首次响应时间、闭环时间和闭环率，以便及时跟进社区问题
2. **PR响应监控场景**：开发者需要了解PR的响应效率，确保代码审查及时完成
3. **论坛运营监控场景**：论坛管理员需要了解各板块的响应情况，标记和跟进长期未闭环的问题
4. **CI效率监控场景**：DevOps团队需要监控CI排队时长和构建时长，优化开发体验，经评估暂时无法支撑，opengauss在openlibing平台没有构建数据
5. **社区健康度评估场景**：社区管理者需要了解TopN问题，掌握社区整体健康状况（当前已存在）

## 3 需求验收标准

> 明确需求完成的标志，必须是可量化、可测试的。

**验收标准:**

- [ ] 看板增加Issue首次响应时间指标，支持按SIG筛选（SQL、Storage、Tools、oGRAC、QA、Security、AI、Plugin、OPS），支持"全量"和"核心仓"视图切换
- [ ] Issue响应指标满足牵引目标：工作日首次响应<24H、闭环时间<7Day、闭环率80%+
- [ ] 支持过滤good first issue、Roadmap等特定类型Issue
- [ ] 看板增加PR首次响应时间指标，支持"全量"和"核心仓"视图切换
- [ ] 看板增加论坛首次响应时间指标，按板块、标签类型分开度量，前端只展示问题求助板块数据
- [ ] 论坛响应指标满足牵引目标：工作日首次响应<24H、闭环率80%+
- [ ] 论坛增加新标签类型，用于标记有响应但后续长时间原提问者未出现的问题

> 简述实现逻辑（如：数据流向、模块改动、新增配置项等），作为任务拆解的理论依据。

**逻辑方案:**

1. **数据采集层**：当前Issue/PR数据已具备，通过论坛API获取帖子数据板块标签等数据
2. **数据处理层**：计算首次响应时间、闭环时间、闭环率等指标，按SIG/板块/标签维度聚合
3. **展示层**：在看板总览页面增加新的数据卡片和图表，支持"全量"/"核心仓"视图切换
4. **标签系统**：扩展论坛标签类型，新增"待确认"标签用于标记有响应但提问者未回复的问题
