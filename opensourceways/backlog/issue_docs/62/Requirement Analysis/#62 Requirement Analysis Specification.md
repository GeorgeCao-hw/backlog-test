# Description Agent 需求分析说明书

## 1. 基础信息

* **需求链接**: https://github.com/opensourceways/backlog/issues/62
* **需求名称**: Description Agent (Issue/PR 描述合规性检查代理)
* **开发责任人**: drizzlezyk
* **设计目标**: 引入大语言模型（LLM），自动对用户提交的 Issue 和 Pull Request (PR) 的描述和标题进行规范性、完整性审查。当描述不符合社区规范时，自动回复缺失信息和改进建议，并打上对应标签，以提升社区 Issue/PR 的质量和沟通效率。

---

## 2. 需求场景说明

**场景说明:**
在开源社区中，开发者提交的 Issue 或 PR 描述往往缺乏必要的上下文、复现步骤或测试结果，导致维护者需要反复沟通确认，降低了处理效率。为了解决这一痛点，需要一个基于大模型的智能代理（Description Agent）能够：
1. **自动获取规范**：根据 Issue/PR 的类型（如 Feature, Bug），自动加载对应的社区模板规范。类型推断主要通过标题的前缀（如 `[Feature]`）及配置映射来实现。
2. **内容审查与合规判断**：利用大模型分析 Issue/PR 的标题和描述，判断是否满足模板要求，是否存在敏感信息（通过安全审核接口）。
3. **智能反馈与打标**：如果不合规，自动生成包含缺失项和修改建议的评论，并为该 Issue/PR 打上 `need-detail-desc` 标签；如果合规，则移除该标签。
4. **图像解析支持**：提取描述中的图片 URL，能够解析并下载图片（LogImageExtractor），提取错误日志图片中的文本和环境信息，辅助大模型进行综合判断。
5. **精准过滤**：结合 Webhook Handler，只处理处于 `open` 或 `opened` 状态且在配置白名单仓库中的 Issue/PR。

---

## 3 需求验收标准

**验收标准:**
1. **准确性**：能够准确解析大模型返回的 JSON 结果（兼容 Markdown 代码块及特殊字符转义），对合规与否的判断准确率达到预期。
2. **安全性**：输入大模型前和输出大模型后，均需通过安全审核 API (`audit_client`)，拦截任何违规/敏感内容。
3. **闭环逻辑**：用户修改描述后（触发 webhook 更新事件），代理能重新评估。若合规，则自动移除 `need-detail-desc` 标签并回复通过信息。
4. **健壮性**：有效处理大模型调用失败、网络超时、图片解析失败等异常，保证主服务不崩溃，并记录准确的日志。

---

## 4. 需求设计与分解

### 4.1 核心逻辑方案

**逻辑方案:**
采用“Webhook 事件驱动 + 大模型分析 + 安全审核 + 状态反馈”的架构。
- **数据流向**：GitCode Webhook 事件 -> 校验状态（仅处理 open 状态和白名单仓库） -> 敏感词审核 -> LLM 评估 -> 输出结果审核 -> GitCode API（回复与打标）。
- **模块改动**：新增 `agent/description_agent.py`，实现 `DescriptionComplianceAgent` 和 `LogImageExtractor`。修改 `webhook/handlers.py` 以集成该代理。
