### 3.1 功能测试专项

> 参考测试设计方向
> * API 语义验证：验证 HTTP 状态码（2xx, 4xx, 5xx）的使用是否符合 RESTful 规范。
> * 边界与非法输入：验证大数据量、空字段、特殊字符及非法 JSON 格式的拦截能力。
> * 业务状态机闭环：验证资源从"创建中"到"运行中"再到"已释放"的全生命周期逻辑。

#### 测试用例设计

**1. API接口正常查询测试（github_id）**

* **对应task链接:** 架构设计文档 TASK1 - 设计和实现数据中台 API 接口逻辑
* **测试步骤:**
  1. 准备有效的API Key
  2. 调用接口：`GET /api/v1/users/email?github_id=testuser`
  3. 在请求头中携带：`X-API-Key: valid-api-key`
* **预期结果:**
  - HTTP状态码：200
  - 响应格式符合设计规范：
    ```json
    {
      "code": 200,
      "message": "success",
      "data": {
        "email": "testuser@example.com",
        "github_id": "testuser",
        "gitcode_id": "testuser"
      }
    }
    ```

**2. 参数缺失测试**

* **对应task链接:** 架构设计文档 TASK1
* **测试步骤:**
  1. 调用接口时不提供github_id和gitcode_id参数
  2. `GET /api/v1/users/email`
* **预期结果:**
  - HTTP状态码：400
  - 响应格式：
    ```json
    {
      "code": 400,
      "message": "Missing required parameter: github_id or gitcode_id",
      "data": null
    }
    ```

**3. 特殊字符输入测试**

* **对应task链接:** 架构设计文档 TASK1
* **测试步骤:**
  1. 使用包含特殊字符的参数（如SQL注入尝试）
  2. `GET /api/v1/users/email?github_id='; DROP TABLE users; --`
* **预期结果:**
  - 参数验证失败，返回400错误或404（用户不存在）
  - 不应导致SQL注入或系统错误

**4. 超长参数测试**

* **对应task链接:** 架构设计文档 TASK1
* **测试步骤:**
  1. 使用超长字符串作为参数（如1000个字符）
  2. `GET /api/v1/users/email?github_id=aaaa...（1000个字符）`
* **预期结果:**
  - 参数验证失败，返回400错误或404（用户不存在）
  - 不应导致系统崩溃或内存溢出

### 3.2 安全与隐私测试专项

> 参考测试设计方向
> * 最小特权原则 (PoLP)：验证服务账户（Service Account）是否无法越权操作未授权的资源。
> * 软件供应链审计：通过 SBOM 检查，验证容器镜像中是否存在已知的高危 CVE 漏洞。
> * 敏感信息外泄防护：检查日志、监控指标及 API 报错中是否夹带了明文密钥或隐私数据。

#### 测试用例设计

**1. API Key认证测试 - 无API Key**

* **对应task链接:** 架构设计文档 TASK2（SEC-3）- 实现API Key验证逻辑
* **测试步骤:**
  1. 调用接口时不提供X-API-Key请求头
  2. `GET /api/v1/users/email?github_id=testuser`
* **预期结果:**
  - HTTP状态码：401
  - 响应格式：
    ```json
    {
      "code": 401,
      "message": "Invalid API Key",
      "data": null
    }
    ```

**2. API Key认证测试 - 无效API Key**

* **对应task链接:** 架构设计文档 TASK2（SEC-3）
* **测试步骤:**
  1. 使用无效的API Key
  2. 在请求头中携带：`X-API-Key: invalid-api-key`
* **预期结果:**
  - HTTP状态码：401
  - 响应格式同上

**3. API访问频率限制测试**

* **对应task链接:** 架构设计文档 TASK2（SEC-4）- 实现API访问频率限制
* **测试步骤:**
  1. 使用同一个API Key在1分钟内连续发送超过600次请求
* **预期结果:**
  - 前600次请求成功（返回200或404等正常状态码）
  - 第601次及之后的请求返回429错误：
    ```json
    {
      "code": 429,
      "message": "Rate limit exceeded",
      "data": null
    }
    ```

**5. 日志脱敏验证测试**

* **对应task链接:** 架构设计文档 TASK3（SEC-5）- 实现日志脱敏逻辑
* **测试步骤:**
  1. 成功调用API获取用户邮箱
  2. 检查API访问日志
* **预期结果:**
  - 日志中邮箱地址应脱敏处理（如：`j****e@example.com`）
  - 日志中不应出现明文邮箱地址
  - 日志应包含必要的审计信息（API Key标识、时间戳、请求参数、响应状态码）

**6. API Key加密存储验证**

* **对应task链接:** 架构设计文档 TASK2（SEC-2）- 实现API Key加密存储
* **测试步骤:**
  1. 生成一个API Key
  2. 直接查询数据库中存储的API Key
* **预期结果:**
  - 数据库中存储的API Key应为加密后的密文（AES-256）
  - 不应存储明文API Key

**7. SQL注入防护测试**

* **对应task链接:** 架构设计文档 TASK1 - API接口实现
* **测试步骤:**
  1. 使用SQL注入攻击字符串作为参数
  2. 尝试多种SQL注入模式：
     - `' OR '1'='1`
     - `'; DROP TABLE users; --`
     - `' UNION SELECT * FROM users --`
* **预期结果:**
  - 所有SQL注入尝试均失败
  - 返回404（用户不存在）或400（参数错误）
  - 不应导致数据泄露或数据库损坏

**8. 敏感数据泄露检查 - API响应**

* **对应task链接:** 架构设计文档 TASK1
* **测试步骤:**
  1. 查询用户邮箱
  2. 检查API响应是否包含额外的敏感信息
* **预期结果:**
  - API响应只包含必要的信息（email、github_id、gitcode_id）
  - 不应泄露数据库内部字段（如：用户ID、密码哈希、手机号等）
