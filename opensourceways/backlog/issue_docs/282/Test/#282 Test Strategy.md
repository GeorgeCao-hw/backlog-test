### 3.1 功能测试专项

> 参考测试设计方向
> * API 语义验证：验证 HTTP 状态码（2xx, 4xx, 5xx）的使用是否符合 RESTful 规范。
> * 边界与非法输入：验证大数据量、空字段、特殊字符及非法 JSON 格式的拦截能力。
> * 业务状态机闭环：验证资源从"创建中"到"运行中"再到"已释放"的全生命周期逻辑。

**1. VALIDATION 状态触发打标（task1）**：Gitcode Issue 状态变更为 `VALIDATION`，Bot 接收 Webhook 事件后自动打 `resolved` label。

* **对应 task 链接**: https://github.com/opensourceways/backlog/issues/282
* **预期结果**: Issue 在 60s 内被打上 `resolved` label，Bot 日志无异常。

**2. DONE 状态触发打标（task1）**：Gitcode Issue 状态变更为 `DONE`，Bot 接收 Webhook 事件后自动打 `resolved` label。

* **对应 task 链接**: https://github.com/opensourceways/backlog/issues/282
* **预期结果**: Issue 在 60s 内被打上 `resolved` label，Bot 日志无异常。

**3. 非目标状态不触发打标（task1）**：Issue 状态分别变更为 `TODO`、`ACCEPTED`、`WIP`、`REJECTED`，Bot 不打 `resolved` label。

* **对应 task 链接**: https://github.com/opensourceways/backlog/issues/282
* **预期结果**: 上述状态变更后，Issue 无 `resolved` label 变化，Bot 日志无误操作记录。

**4. 统计看板采集状态字段（task2）**：Gitcode Issue 状态字段更新后，统计看板定时任务执行，数据表中可查到对应 Issue 的状态字段值。

* **对应 task 链接**: https://github.com/opensourceways/backlog/issues/282
* **预期结果**: 看板查询接口返回的 Issue 状态字段与 Gitcode 侧一致。

### 3.3 集成测试专项

> 参考测试设计方向
> * 协议兼容性：验证不同版本的组件间（如旧版网关与新版后端）通过 gRPC/HTTP 通信的兼容性。
> * 分布式事务/最终一致性：验证跨数据库操作或跨服务调用时，在网络波动下的数据对齐情况。
> * 全链路追踪覆盖：确保 TraceID 在所有微服务节点间透传，无断链现象。

**1. Webhook 事件 → Bot 打标链路验证**：模拟 Gitcode 发送 Issue 状态变更 Webhook，验证 Bot 全链路（接收 → 解析状态 → 调用 Gitcode API 打标）执行正确，下游 `resolved` label 依赖方（如 Issue 关闭流程、统计看板）数据一致。

* **对应 task 链接**: https://github.com/opensourceways/backlog/issues/282
* **预期结果**: Webhook → Bot → Gitcode API 链路无断链，打标结果在依赖 `resolved` label 的下游可见。

**2. 统计看板数据链路验证**：Gitcode Issue 状态字段变更后，统计看板数据采集任务正常运行，数据库中 Issue 状态字段与 Gitcode 侧最终一致。

* **对应 task 链接**: https://github.com/opensourceways/backlog/issues/282
* **预期结果**: 数据采集后，看板查询 Issue 状态字段与 Gitcode 实际状态一致，无数据延迟超过采集周期。
