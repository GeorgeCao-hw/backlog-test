## 3. 生产环境验证

> **参考方向**：变更后如何快速确认"系统是好的"且功能符合预期。

**验证方式：**

_**核心链路拨测**：_

```bash
# 1. 验证正常登录（无验证码场景）
curl -s -X POST https://<host>/api/v1/login \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@test.com","password":"correct_password"}' \
  | jq '.token'  # 期望返回 token

# 2. 验证失败计数触发（默认阈值=1，第1次失败后计数=1，下次登录即触发验证码）
curl -s -X POST https://<host>/api/v1/login \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@test.com","password":"wrong"}' \
  | jq '{retry_num}'
# 期望响应: {"retry_num": 1}（本次失败后计数已达阈值，下次登录将返回 need_captcha=true）

# 3. 获取验证码
CAPTCHA=$(curl -s https://<host>/captcha | jq -r '.captcha_id')
echo "Captcha ID: $CAPTCHA"

# 4. 核心健康检查
curl -s https://<host>/health | jq '.status'
```

_**日志特征匹配**_：观察生产环境日志，确认：
- 无新增 `connection refused` 错误（Redis 连通性正常）
- 登录失败日志包含 `login_fail` 关键字
- 验证码校验日志包含 `captcha_verify` 关键字
- 新版本号已生效

_**业务指标闭环**_：
- 管理员登录成功率无明显下降（正常登录不应触发验证码）
- Redis 内存使用无异常增长（Key TTL 正常过期）
- 登录接口 P99 延迟无显著增加（Redis 查询在 1ms 以内）

## 4. 回滚方案

> **原则**：回滚必须是受控且经过验证的，**禁止现场临时拼凑命令**。

> 出现以下任意一种情况，必须立即中断变更并启动回滚：
> 1. **指标异常**：错误率超过 5% 或 P99 延迟增加超过 50% 且持续 2 分钟。
> 2. **核心阻塞**：主要业务链路中断，且无法在 10 分钟内定位根因。
> 3. **不可抗力**：变更期间发生严重的云服务中断或网络分区。

> 参考：
> * **代码/版本回滚**：执行 `kubectl rollout undo` 命令或重新部署上一个稳定版本的镜像。
> * **配置回滚**：将配置中心（如 Nacos/Apollo）切换回上一个版本的快照。
> * **数据回滚**：执行数据库倒滚脚本或恢复快照（注意数据一致性评估）。

**回滚执行路径：**

| 步骤 | 回滚动作 | 执行命令/方式 | 预期结果 |
|--------|------|----------------------------------------------------|----------------------------|
| **R1** | 配置还原 | 将 Captcha 相关配置项删除或还原为变更前快照（如配置中心支持版本回退） | 配置项恢复至变更前状态 |
| **R2** | 版本回退 | `kubectl rollout undo deployment/app-cla-server` | 系统恢复至上一个稳定版本镜像，旧登录逻辑恢复 |
| **R3** | 验证回滚 | 执行核心链路拨测脚本，确认正常登录恢复（登录响应不含 need_captcha/retry_num 字段），captcha 接口不再存在（404） | 服务恢复到变更前状态，功能正常 |
| **R4** | Redis 清理 | 可选：`redis-cli --scan --pattern "captcha:*" | xargs -r -L 100 redis-cli DEL` 分批清理残留验证码 Key（-r 避免空输入报错，生产安全） | 残留验证码 Key 已清除（也可等待 TTL 自动过期） |

**回滚影响说明：**
- 回滚后登录接口恢复为无验证码模式，暂时失去防暴力破解保护
- Redis 中残留的验证码和失败计数 Key 有 TTL 会自动过期，无数据一致性问题
- 回滚不影响已登录用户的 Session/Token
