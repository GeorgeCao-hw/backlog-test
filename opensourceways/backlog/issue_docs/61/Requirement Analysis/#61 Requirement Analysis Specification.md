# GitCode Issue 自动化管理机器人需求分析说明书

## 1. 基础信息

* **需求链接**: https://github.com/opensourceways/backlog/issues/61
* **需求名称**: GitCode Issue 自动化管理机器人 (GitCode Issue Management Bot)
* **开发责任人**: [drizzlezyk](https://github.com/drizzlezyk)
* **设计目标**: 实现一套自动化的 Issue 处理系统，通过识别 Issue 标题、状态、关联 PR 以及用户/负责人的互动频率，自动执行打标、回复、状态流转和关闭操作，提升社区治理效率。

---

## 2. 需求场景说明

**场景说明:**
目前社区 Issue 依赖人工维护，处理效率低且容易遗漏超期未响应的情况。为了解决重复性的打标和状态跟踪问题，用户需要一个机器人能够：
1. **自动分类**：根据标题前缀自动添加功能/缺陷标签。
2. **闭环管理**：识别已解决（已合并关联 PR）的 Issue 并打上 `resolved` 标签。
3. **超期处理**：对长时间未响应的 `resolved` 或 `wait_response` 状态的 Issue 进行自动提醒、标记 `stale` 甚至自动关闭。
4. **互动恢复**：当用户在 `stale` 状态下重新互动时，自动恢复 Issue 正常状态。

---

## 3 需求验收标准

**验收标准:**
1. **准确性**：100% 正确识别并处理 [Feature], [Bug], [Doc] 等标题前缀的 Issue。
2. **时效性**：机器人能按设定的周期（如每天一次扫描）或实时（Webhook）处理 Issue 状态。
3. **闭环逻辑**：符合“关联 PR 已合并 -> Issue 自动 resolved -> 7天无响应 -> stale -> 4天无响应 -> close”的完整链路。
4. **可量化价值**：经测试，社区维护者处理 Issue 的手动操作（如手动打标、催促回复）耗时预计减少 70% 以上。

---

## 4. 需求设计与分解

### 4.1 核心逻辑方案

**逻辑方案:**
采用“规则引擎 + 定时任务 + 实时回调”的架构。
- **数据流向**：GitCode API -> 机器人 Client -> 规则引擎判定 -> 数据库状态快照 -> 机器人执行 API（评论/标签）。
- **模块改动**：新增 `rules` 模块用于扩展不同场景的自动化策略，新增 `core/database` 用于维护 `IssueState`（记录最后一次通知时间）。

### 4.2 任务清单

| 任务 ID | 任务描述 (Task Description) | 预期产出 (Deliverables) | 预期工作量（人天） |
| :--- | :--- | :--- | :--- |
| **TASK1** | 实现标题前缀自动识别与打标逻辑 | `IssueTitleLabelRule` 代码 | 1 |
| **TASK2** | 实现 `resolved` 到 `stale` 到 `closed` 的状态流转逻辑 | `StaleCommentRule` 等代码 | 3 |
| **TASK3** | 封装 GitCode API 客户端（含 Token 鉴权与模型映射） | `GitcodeClient` 模块 | 2 |
| **TASK4** | 开发 Webhook 服务，支持实时事件处理 | `WebhookServer` 模块 | 2 |
| **TASK5** | 编写单元测试并确保覆盖率 > 20% | `tests/` 目录下测试用例 | 2 |
